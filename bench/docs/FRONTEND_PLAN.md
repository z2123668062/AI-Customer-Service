# 记忆面板前端方案

## 0. 目标

这个前端不是产品，是**论文的证据装置**。它只需要支撑三个论断，多一个功能都不做。

| 论断 | 界面要证明的事 |
|---|---|
| 规模解耦 | 同一批卡片能覆盖很长的历史跨度，一屏看完 |
| 时间可寻址 | 卡片带绝对日期，且能按时间排列 |
| 事实级可审计 | 每条记忆能点开看到它来自哪几句原文，能改、能删、能回滚 |

## 1. 现状盘点

不用新建项目，现有 `frontend/` 已经有相当完整的骨架。

| 已有 | 位置 |
|---|---|
| 三页签（记忆总览 / 淘汰日志 / 演示区） | `views/memory_page.py` |
| 统计指标卡（总数、有效、被取代、撤销） | 同上 |
| 卡片列表与详情读取 | `api_client.fetch_cards / fetch_card` |
| 编辑、删除、恢复、回滚、彻底删除 | 同上 L177 到 L213 |
| 剪断因果边 | 同上 |
| 对话页与本轮记忆展示 | `views/chat_page.py` |
| 后端全套 CRUD | `app/api/v1/endpoints/memory.py` |

**已经能跑通「改一张卡」这件事了。** 缺的不是功能，是三个视图。

## 2. 缺的三块

### 2.1 来源原文回跳（最要紧）

卡片表两列 `canonical_name` 和 `source_message_ids` 已经写进去了（293/293 全填），但**接口没暴露**，所以界面上看不见。

这是「可审计」唯一的硬证据：不是我说卡片对，是你能看到它从哪句话来的。

### 2.2 按实体分组

现在是一张平铺的 DataFrame。按人、按地点分组之后，才看得出「系统记得这个人的哪些事」，也才能支撑「实体锚定」这个说法。

### 2.3 时间轴

现在按 id 或时间排序的表格。要一条横向时间轴，让「记忆覆盖了多长的历史」这件事一屏可见。

## 3. 后端改动（两处，都不大）

### 3.1 列表项补两个字段

`app/models/schemas.py` 的 `CardItem` 加：

```python
canonical_name: Optional[str] = Field(default=None, description="节点卡标准名（人/地/物）")
source_message_ids: Optional[list[int]] = Field(default=None, description="来源原文 id")
```

只加字段，不改查询。ORM 对象本来就有这两个属性，`from_attributes` 会自动带出来。

### 3.2 详情补来源原文

`CardDetail` 加一个 `sources`：

```python
class SourceMessage(BaseModel):
    id: int
    role: str
    content: str
    created_at: Optional[datetime] = None

class CardDetail(CardItem):
    ...
    sources: list[SourceMessage] = Field(default_factory=list)
```

在 `GET /memory/{card_id}` 里按 `source_message_ids` 查一次 `messages` 表填进去。

**不建议单独开接口。** 详情一次请求拿全，前端少一次往返，也少一个可能失败的点。

### 3.3 不改的部分

不新增路由，不改写路径，不动检索。前端所有编辑操作走的是已有的 PATCH / DELETE / restore / rollback。

## 4. 界面设计

技术选择：**继续用 Streamlit**，不引入新栈。

理由三条：现有组件够用；改起来是几十行的事；答辩现场一条命令起服务，不用 `npm run build`。为了动画换 React 不划算。

### 4.1 总览页（改造）

```
┌─────────────────────────────────────────────────┐
│  记忆总数 293   有效 290   被取代 3   节点 37    │
├─────────────────────────────────────────────────┤
│  [ 全部 ] [ 按实体 ] [ 按时间 ]      ← 新增分段   │
├─────────────────────────────────────────────────┤
│  2023-05-07 │ 事件 │ Caroline 参加了 LGBTQ 支持小组│
│  2023-06-02 │ 事件 │ Melanie 在陶艺工作坊...      │
│  当前       │ 事实 │ Melanie 是跑步爱好者          │
└─────────────────────────────────────────────────┘
```

**按实体**视图下，先出一列实体（人或地点），点进去展开该实体的全部卡。分组直接用 `entities[0]` 或 `canonical_name`，前端算，不动后端。

**按时间**视图下，按 `event_time or created_at` 排，每行带日期。没有时间的卡单独一块，标「时间未知」。这个标注本身就是诚实边界的一部分。

### 4.2 卡片详情（扩展）

```
┌─────────────────────────────────────────────────┐
│  事件 · 2023-06-02 · 有效                        │
│  Caroline 参加了 LGBTQ 支持小组…                 │
├─────────────────────────────────────────────────┤
│  📎 来源原文（2 条）                             │
│     #18  Caroline: I went to the support group… │
│     #19  Caroline: It really helped me…         │
├─────────────────────────────────────────────────┤
│  ✏️ 修改正文   [ 文本框 ]  [ 保存 ]              │
│  🗑 删除      ↺ 回滚到上一版                     │
├─────────────────────────────────────────────────┤
│  🔗 关联（3 条边）                               │
│     led_to → LGBTQ 支持中心                     │
└─────────────────────────────────────────────────┘
```

「来源原文」区块是新加的，其余都是现成的。

**修改要明确告知后果**：保存等于新建一个版本、旧版本下架、可以回滚。这句话必须写在按钮下面，否则用户以为是在原地改。

### 4.3 对话页联动

现在对话页已经有「本轮记忆」的卡片摘要。加一个链接：点击摘要跳到记忆面板并定位到那张卡。

这是让「可审计」在演示时能连起来的关键一跳：**答错了 → 点开 → 看到是哪张卡 → 看到原文 → 改掉 → 再问一次**。这条链走通一次，比十页 PPT 有用。

| 编号 | 内容 | 用在哪 |

## 7. 风险

**一，错卡会出现在截图里。**

之前抽到过「Melanie is planning to adopt a child」，原文里那个人是 Caroline。

**截图前必须抽检。** 65 张事件卡和 37 个节点卡过一遍人名归属，错的先修。审出来的错卡本身是好事（说明可审计有效），但拿一张明显的错卡当论文配图，观感是反的。

**二，演示依赖四个中间件。**

后端 + SQLite + Qdrant + Redis。任何一个没起，界面就是一片红。

答辩前准备一个**预制数据库快照**，一条命令还原，不要现场灌库（灌一次 38 分钟）。

**三，Streamlit 的重跑模型。**

每次交互整个脚本重跑，编辑之后如果状态没存好，会回到旧值。改动要用 `st.session_state` 承接，别依赖局部变量。

## 7.5 实施进度（2026-11-01）

**已落地**

| 项 | 位置 | 说明 |
|---|---|---|
| 列表项补 `canonical_name` / `source_message_ids` | `schemas.py` | 只加字段，不改查询 |
| 详情补 `sources` | `schemas.py` + `memory.py` | 按来源 id 回查 messages，同一请求返回 |
| 视觉重做 | `theme.py` + `.streamlit/config.toml` | 档案柜方向：纸白底、墨色字、墨蓝唯一强调色、等宽日期 |
| 三视图 | `views/memory_page.py` | 列表 / 按实体 / 时间轴 |
| 来源原文区 | `views/memory_page.py` | 按文字重合度排序，前三条展开，其余折起 |

单测 261 全过，HTML 组件转义已验证。

**待验**：起后端 + Streamlit 后截图，确认时间轴在真实数据下的观感（需要审批启动进程）。

**一个必须写进论文的边界**：`source_message_ids` 是**批次级**的——抽取以 8 条为一批，一张卡记的是整批，不是逐句对应。界面上已明确标注"只有批次来源，没有逐句对应"，不能当成精确溯源来讲。

**事故记录**：用 `TestClient(app)` 做接口冒烟时进了 lifespan，触发启动回填，往 `s0d.db` 写了 79 张重复卡和 35 条边。已按 `created_at >= 2026-11-01` 精确删除，恢复到 293 卡 / 4 caused_by / 90 led_to / 3 supersedes。

根因是 bench 的多个库共用全局 journal（`data/extract_journal.log`），绕开 `prepare_env` 就会看到别处的水位。**以后任何要跑起来的验证，都必须先 `prepare_env` 或把 journal 指到临时文件。**

## 8. 不做的部分

明确写下来，避免范围蔓延。

- 不做卡片关系图谱可视化（要装 graphviz，收益低）
- 不做动画（论文是静态截图，动画只对现场演示有用，且容易卡）
- 不做移动端适配
- 不做多用户
- 不做记忆的手工新建表单（虽然这是个好方向，但它属于功能增量，本节只做「看、审、改」）
