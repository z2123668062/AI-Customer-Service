# 12 个模块的实测对账

sample 0，419 条对话，209 张卡，50 道题。下表每一行的「证据」都是跑出来的数，不是设计文档里的说法。

## 一、真正干活的

| 模块 / 机制 | 干了什么 | 证据 |
|---|---|---|
| `reranker`（精筛） | 唯一在筛东西的环节 | 每题判 110 张，占 90% 延迟，把 110 压到 1.8 |
| `extractor` | 卡片的唯一来源 | 419 条抽成 209 张，52 批全成功 |
| `retriever` 实体入口 | 86/88 轮走这条 | `triage`: hit 86 / fault 2 |
| `gate.judge_shortlist` | 精筛的判定内核 | 110 次调用/题 |
| `store` / `writer` | 落库与提交 | 209 卡 + 5 边 |
| `journal` | 水位推进 | `watermark` 从 0 推到 419 |
| `injector` | 渲染 | 注入率 88.6% |

## 二、用上了但基本没起作用

| 模块 / 机制 | 为什么没起作用 |
|---|---|
| `gate.judge_page_fault`（分诊） | 44 道题全部判 yes，一次都没筛掉。白付 1.2 秒/题，占延迟 4.4% |
| `gate.judge_supersede`（取代判定） | 209 张卡只判出 3 张 superseded。LoCoMo 是两人闲聊，没有「我搬家了」这种改写 |
| `gate.judge_backfill`（因果回填） | 全库只有 5 条边。顺线一跳基本无邻居可扩 |
| `writer` 判重 | 只判完全同文。「Melanie has children」出现了两次，两张家人口味的卡语义重复却都留着 |
| `pool` 实体倒排 | 用了，但它的「高命中」正是 110 个候选的来源。副作用大于贡献 |

## 三、完全没用上的

| 机制 | 为什么零命中 |
|---|---|
| `pool` 时间轴 / `by_time_range` | `event_time` 在 209 张卡里 0 张有值，时间轴是空的 |
| `retriever` L2 原文兜底 | 44 题只有 1 题走了缺页回源，L2 几乎没被调用 |
| `retriever` 语义路 | 命中路径下根本不执行（第一轮改动前），86/88 轮都是命中 |
| `explicit` 显式通道 | `is_explicit` 是中文正则（记住、记一下、别忘记），英文对话永不命中 |
| `consolidator` 的「重要声明」触发 | `_IMPORTANT_RE` 同样是中文（我叫、我住在、我过敏），英文场景失效 |
| `consolidator` 的「空闲收口」 | 需要静默 30 分钟，评测里没有这个窗口 |
| `evictor` | `event_time` 全空，目标过期规则无从判定；回放时还得手动关掉 |
| `pool` 的 SLRU 两段 + 换出记录簿 | 容量 512，实际 206 张，从未触顶，替换策略没被激活 |
| `gate.judge_ownership` | V1 明确未实现，恒返回 archive |
| 编辑层（revoke / purge / rollback / cut_edge） | 评测完全没有触及 |

**三触发里只有「攒批」一条在跑**，52 批全部由它触发。另外两条在英文数据上是死代码。

## 四、设计里有卖点但这份数据测不出来的

- **版本化**（supersedes 边 + 状态推导）。卖点是「用户搬了家，旧地址自动失效」。LoCoMo 没有这类冲突，所以这个能力在报告里只能靠单元测试背书，拿不出基准分数。
- **被遗忘权**（revoke / purge）。同上。
- **换出与重入**（SLRU + 换出记录簿）。卡数没到容量上限，机制从未运转。

这三个不是缺陷，是「数据没给机会」。论文里要讲，得另配一组构造数据，不能指望 LoCoMo。

## 五、除了已知那几项，还能挖的地方

按预期收益从高到低。

### 1. token 预算被当成了张数配额

现在注入 8 张卡，生成侧 prompt 平均 650 token。而 full-context 基线是 16 到 26K token。

我们在省一个根本不需要省的东西。

LoCoMo 论文自己说，这个基准测的是「同等质量下省多少 token」。省 25 倍但正确率掉一半，不算赢。应该把 `INJECT_MAX_CARDS` 换成一个 token 预算，比如 3000 token，能塞多少塞多少。这个改动的成本是零（不用重灌、不用改检索），收益可能比前面所有改动加起来大。

### 2. 注入集没有来源多样性约束

multi-hop 只答对 57%，结构性原因是：一道多跳题的证据分在两个不同会话里，而语义相似度排序很可能把两张都来自同一会话的卡排在前面，另一张被截断。

解法不是加新机制，是在截断规则上加一条约束：候选里如果覆盖了多个 session，保证至少各留一张。这属于组合选择问题，但可以先做最简版，比如「按 session 分组后轮流取」。

### 3. 卡片缺 provenance，这才是原文通道的正解

我之前说「L2 原文通道常态化」，但没想清楚关键词怎么取。`build_l2_keywords` 会把 what、did、does 这类词也算进去，OR LIKE 一查命中一片，噪声压不住。

真正的解法是给卡片记住它来自哪几条消息（`source_message_ids`）。注入时把这几条原文无损带上，一次解决两个问题，既补回卡片的有损部分，又不需要猜关键词。

这是个 schema 改动，要重灌，但可以和「带时间戳重灌」一起做，没有额外成本。

### 4. 抽取把列表压成了概括

列表题丢分很集中。q15 标准答案四个活动，我们答两个还编了一个；q32 三个事件答成一个；q38 六个活动答成两个。

抽取器现在按「一句话原子事实」产出，一条消息里四个活动会被压成「Melanie 喜欢各种活动」。这种损失到检索阶段无法补救。抽取提示词加一句「列表型事实逐项列出」，和日期一起重灌，顺手的事。

### 5. 会话边界在抽取时丢失

19 个会话在入库时全部挂在同一个 `session_id` 下，抽取按 8 条一批切开。模型完全不知道哪里是新的一天。

后果是它会跨会话合并事实。「Melanie 有个老公」和「结婚五年了」来自两个不同 session，被当成同一条时间线上的补充。时间戳能解决「哪天」，会话边界还得作为独立信号进抽取输入。

### 6. 窗口长度是个免费的消融

现在窗口固定 10 条，而且永远是对话最末尾的 10 条，与问题基本无关，纯属噪声。

把它设成 0 跑一遍，就能知道这 10 条到底帮了忙还是添了乱。三档（0 / 10 / 40）加起来不到半小时，不用重灌，不用改代码。

### 7. 消融至今没做

验收清单第 5 条「哪个模块贡献最大」，到现在还是空的。

按现有数据猜，精筛是唯一真正在干活的，gate 和因果边大概率是负资产（白花时间、零贡献）。但这得跑出来才算数。做一次三组消融（关 gate、关精筛、关原文回填），每组 50 题，一小时能出结论。

### 8. 只有一段对话

10 段对话只测了第 1 段。这一段的两个人正好都在聊生育、领养、性别认同，话题高度集中。换一段（比如工作相关的）结论可能完全不同。全量之前至少该补到 3 段。

---

## 六、一句话总结

12 个模块里，真正在起作用的其实只有三个半：抽取器、精筛、注入器，加上一半的检索。

快表的时间轴、L2 原文、语义路、显式通道、因果回填、淘汰、替换策略，这些要么零命中，要么在英文数据上是死代码。

这个结论不好看，但它比继续加新功能有用。下一步该做的不是补模块，是把已经在跑的这几个用对。
