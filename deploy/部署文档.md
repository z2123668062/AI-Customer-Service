# 部署文档

> 记录对象：2026-11-18，把「记忆助手」从本机 Docker 跑通，到腾讯云 CVM 公网可访问的完整过程。
> 读者：第一次接触部署的人；以及要拿它当模板做下一个项目的人。
> 配套文件：`Dockerfile`、`Dockerfile.web`、`nginx.conf`、`docker-compose.yml`、`故障清单.md`。
> 这篇文档的重点不是「命令是什么」，是「为什么这么决定」。命令会过时，判断不会。

---

## 一、这篇文档怎么用

别从头读到尾。照着自己项目做，卡在哪一步就翻哪一步。

第三到第五步是写配置文件，对着自己的项目改。第七步以后是服务器上的操作，跟代码无关。

如果你只想先建立概念，读第二节和第九节就够。

---

## 二、全程地图

一句话概括这次做的事：把「这台机器上凑巧装好的东西」变成「一份能重放的清单」。

十个步骤，分三段。

打包在前六步，全部在本地完成，目标是同一个 compose 文件在自己电脑上全绿。没跑通就上服务器，等于把两个问题叠在一起查。

第七步是服务器准备，跟业务代码毫无关系，但少一样就跑不起来。

第八到第十步把两边接起来，然后分层验收。

| 步骤 | 干什么 | 产出 |
|---|---|---|
| 1 | 清点依赖 | `requirements-prod.txt` |
| 2 | 后端镜像 | `deploy/Dockerfile` |
| 3 | 前端镜像 | `deploy/Dockerfile.web` |
| 4 | 反向代理 | `deploy/nginx.conf` |
| 5 | 编排四个服务 | `deploy/docker-compose.yml` |
| 6 | 本地跑通 | 四个容器 healthy |
| 7 | 服务器准备 | Docker、安全组、SSH |
| 8 | 代码送上服务器 | `git clone` + `.env` + `.htpasswd` |
| 9 | 构建并启动 | 镜像、容器 |
| 10 | 分层验收 | 五层全过才算完 |

---

## 三、第一步：先清点依赖，别急着装 Docker

这一步最容易被跳过，也是后面所有麻烦的源头。

你的项目在本机能跑，靠的不只是代码，还有这台机器上已经装好的东西：Python 版本、几十个第三方包、一个 Redis、一个向量库、`.env` 里的密钥。这些东西平时是隐形的，换台机器全没了。

所以第一个动作是问自己：**如果给我一台刚装好的空系统，我要装什么才能跑起来？**

这次的答案是十三个包：

```
fastapi / uvicorn / pydantic / pydantic-settings / python-dotenv
httpx / openai / SQLAlchemy / aiosqlite / greenlet
redis / qdrant-client / loguru
```

原来那份依赖清单里带着 torch、transformers、sentence-transformers，加起来三个 G。但代码里的 embedding 走的是远程 API，本地模型只有一个懒加载的兜底分支，正常运行时根本不碰。

这就是**隐式依赖**：装着一个用不上的东西。它在你自己的机器上不害你，到了服务器上会变成构建超时、磁盘爆满、镜像拉取慢。

清点的办法不是猜，是把代码里所有 `import` 过一遍，再搜一遍配置项。凡是「装了但没被调用」的，全删。

评估标准很简单：干净虚拟环境里只装这一份清单，测试能全绿，就说明够了。这次 256 个用例全绿，镜像从 3GB 降到 442MB。

## 四、第二步：后端镜像

Dockerfile 的本质是一份「从空系统开始，一步步装出你要的环境」的清单。

这次写了六件事。

**选基础镜像**。`python:3.13-slim` 跟本地开发用的版本对齐，slim 版本去掉了编译工具链和文档，体积小一半。对齐版本这一条别省，本地 3.13、镜像 3.11，很容易在某个库的 API 上翻车。

**先装依赖，再复制代码。** 顺序有讲究：Docker 按层缓存，只要 `requirements-prod.txt` 没变，改代码不会触发重新装包。反过来写的话，你每改一行 Python 都要等两分钟。

**建一个非 root 用户。** 容器被攻破时，攻击者拿到的是 uid 10001，不是 root。

```dockerfile
RUN useradd --create-home --uid 10001 --shell /usr/sbin/nologin appuser \
    && mkdir -p /app/data /app/logs \
    && chown -R appuser:appuser /app
```

这个 10001 后面会咬你一口。宿主机上挂载进来的 `data/` 目录，属主必须也是 10001，否则容器里写不进去。这是 CVM 上必做的一步：

```bash
sudo chown -R 10001:10001 data logs
```

**健康检查打哪个路径。** 这一条今天直接引发了一次故障，见第九节第 1 条。

**启动命令写死成 CMD。** `uvicorn app.main:app --host 0.0.0.0 --port 8000`，注意 `0.0.0.0`。写 `127.0.0.1` 的话容器自己内部能访问，宿主机和别的容器进不来。

**基础镜像和包源做成 build args。**

```dockerfile
ARG PYTHON_IMAGE=python:3.13-slim
FROM ${PYTHON_IMAGE}
ARG PIP_INDEX_URL=https://pypi.org/simple
```

理由很实际：本地在国内网络下要用镜像前缀，服务器上是另一套。参数化之后，同一个 Dockerfile 两边都能用，不用维护两份。

## 五、第三步：前端镜像（多阶段构建）

前端跟后端不一样。Vue 项目需要 Node 才能编译，但编译完之后只需要一堆静态文件，不需要 Node 运行时。

多阶段构建就是解决这个的：第一个阶段用 Node 编译，第二个阶段只把产物拷进 nginx。

```dockerfile
FROM ${NODE_IMAGE} AS build
COPY web/package.json web/package-lock.json ./
RUN npm ci --no-audit --no-fund
COPY web/ ./
RUN npm run build

FROM ${NGINX_IMAGE}
COPY --from=build /web/dist /usr/share/nginx/html
```

最终镜像 73.9MB，里面没有 Node，只有 nginx 加几个 JS 文件。如果用单阶段，光 Node 运行时就是 200MB 起步。

这里有个细节值得说：**本地开发时我们用的是另一个文件 `Dockerfile.web.local`**，跳过 Node 编译，直接把本地已经 `npm run build` 出来的 `dist` 拷进 nginx。

为什么？因为当时从镜像源拉 `node:22-alpine` 卡在 30/56MB 不动。但那只是本地网络的问题，不代表服务器上也不行。所以本地用「跳过编译」的版本验证其余部分，多阶段构建留到服务器上验证。

这是个通用思路：**环境问题挡住你的时候，先把被挡住的那一环换成已知可用的，继续往下走，别停在那里**。但一定要记住哪一环还没验证过，到了正常环境第一件事就是补上。

## 六、第四步：nginx 配置

nginx 在这个架构里干三件事。

**托管静态文件。** Vue Router 用的是 history 模式，`/sessions/123` 这种路径在服务器上其实没有对应文件，所以要 `try_files $uri $uri/ /index.html`，找不到就回退到首页，让前端路由自己处理。

**反向代理 `/api`。** 前端所有请求走相对路径 `/api/v1`，nginx 转给 `backend:8000`。这样前端不用改任何代码，也不用配 CORS，因为同源了。

**流式响应要关缓冲。** 这一条是 SSE 的关键：

```nginx
proxy_buffering off;
proxy_cache off;
proxy_read_timeout 3600s;
add_header X-Accel-Buffering no;
```

不关的话，nginx 会攒够一批才往外发，你看到的「一个字一个字蹦出来」就变成「等十秒然后整段出现」。对话类应用的体验直接崩掉。

这次还加了一层全站鉴权，写在 server 层，所有 location 默认继承：

```nginx
auth_basic "MemoryAssistant";
auth_basic_user_file /etc/nginx/.htpasswd;
```

只有一个 location 显式关掉，`/health`。理由和踩的坑见第九节第 1 条。

## 七、第五步：compose 编排

这一步管的是四个进程之间的关系，不是它们各自怎么跑。

这次的服务划分：

| 服务 | 角色 | 对外 |
|---|---|---|
| web | nginx，托管前端并反代 | **唯一暴露 80** |
| backend | FastAPI，业务逻辑 | 不暴露，仅内网 8000 |
| redis | 热层缓存，可降级 | 不暴露 |
| qdrant | 向量库，可降级 | 不暴露 |

只有 web 映射端口，这一条是硬要求。数据库和缓存的端口一旦映射到宿主机，公网上就多出两个入口，而且它们通常没有鉴权。

**这里有个新手第一大坑：容器里的 localhost 不是宿主机的 localhost。**

`.env` 里写着 `REDIS_HOST=localhost`，本地开发时没问题，因为 Redis 就装在本机。但进了容器，localhost 指向容器自己，那里根本没有 Redis。所以 compose 里必须覆盖：

```yaml
environment:
  REDIS_HOST: redis
  QDRANT_URL: http://qdrant:6333
  DATABASE_URL: sqlite+aiosqlite:///./data/app.db
```

`env_file` 负责注入密钥，`environment` 负责改掉那些「本地能用、容器里错」的值。两个一起用，各管一摊。

**启动顺序要用健康检查卡住，不能靠 sleep。**

```yaml
depends_on:
  qdrant:
    condition: service_healthy
  redis:
    condition: service_healthy
```

backend 需要 Redis 和 Qdrant 都活着才正常干活。写 `sleep 10` 在你自己电脑上经常蒙对，在慢一点的机器上就翻车。健康检查是让 Docker 真的去问一声「你还活着吗」，而不是赌。

**数据要落在容器外面。** SQLite 文件和日志用 bind mount 挂到宿主机，向量库和 Redis 用命名卷。容器随时可以删，数据不能丢。

## 八、第六步：本地先跑通

```bash
docker compose -f deploy/docker-compose.yml up -d --build
docker compose -f deploy/docker-compose.yml ps
```

看到四个都是 `healthy` 才算绿。

这一步的意义不在于「证明它能跑」，在于**把本地问题和服务器问题分开**。如果你跳过这步直接上服务器，出问题时你要同时怀疑代码、配置、网络、权限四个方向。先在本地跑通，服务器上再出问题，嫌疑范围就小得多。

本地全绿之后，这次验证了这些：

健康接口返回 200，首页能打开，发一句中文能逐字返回，记忆能落库，重启容器数据还在，把 Redis 停掉对话仍然能用（慢一点但不崩）。

最后那条是降级验证。软依赖的设计必须实测，因为「我以为它能降级」和「它真的降级了」是两件事。

## 九、第七步：服务器准备

这一层跟你的代码毫无关系。缺一样都跑不起来，而且报错信息通常指向别处。

**装 Docker。** Ubuntu 24.04 自带的源里有，两条命令：

```bash
sudo apt-get update
sudo apt-get install -y docker.io docker-compose-v2
```

装完是 Docker 29.1.3 加 Compose 2.40.3，够用。从 Docker 官方源装会更新一些，但也多一层网络风险，第一次部署不建议给自己加变量。

**配镜像加速。** 编辑 `/etc/docker/daemon.json`：

```json
{
  "registry-mirrors": ["https://mirror.ccs.tencentyun.com"],
  "log-driver": "json-file",
  "log-opts": { "max-size": "50m", "max-file": "3" }
}
```

前半段解决拉镜像慢的问题，腾讯云内网地址不计流量。后半段是日志轮转，Docker 默认把容器日志无限往磁盘写，服务跑一段时间磁盘就满了，而且满得很安静。

**安全组和端口映射是两道门。** 这是最容易搞混的地方。

容器把 80 映射到宿主机，是第一道门。云厂商的安全组放行 80，是第二道门。两道都开，外面才能访问。只开一道的典型症状是「本机 curl 通，外面连不上」。

判断哪道门没开有个技巧：**从外面访问，连接被拒还是超时？**

被拒说明包到了、对方回了 RST，端口是通的，只是没服务在听。超时说明包被丢了，中间有防火墙拦着。一个字的差别，省半小时。

**SSH 别只靠密码。** 这次用的是密钥登录，并且把密码登录彻底关掉：

```bash
# /etc/ssh/sshd_config.d/99-hardening.conf
PasswordAuthentication no
KbdInteractiveAuthentication no
PermitRootLogin prohibit-password
```

改完先 `sudo sshd -t` 校验语法，再 `systemctl reload ssh`。顺序不能反，语法错的配置 reload 会让 sshd 起不来，你就进不去了。

**swap 和时区先看，别盲目加。** 腾讯云的 Ubuntu 镜像自带 2G swap，时区已经是 Asia/Shanghai。网上教程里的 `fallocate -l 2G /swapfile` 在这里是多余的，加了反而占磁盘。先 `swapon --show` 和 `timedatectl` 看一眼再决定。

## 十、第八步：代码送上服务器

两条路：本地构建好镜像推到镜像仓库，服务器拉镜像；或者服务器上拉代码自己构建。

代码量小、服务器网络也通，这次走的是第二条。镜像仓库那套等你有多台机器、或者要做回滚的时候再上，那时候它的价值才显出来。

```bash
git clone https://github.com/<user>/<repo>.git
```

**有两个文件不能靠 clone 拿到，必须单独处理。**

第一个是 `.env`，里面有真实密钥，永远不进仓库。用 scp 传上去，然后 `chmod 600`。

第二个是鉴权密码文件 `.htpasswd`。它也不入库，但 Dockerfile 里有 `COPY deploy/.htpasswd`，文件不存在的话构建会直接失败，报 `file not found`。所以部署顺序里必须包含生成它：

```bash
printf 'admin:%s\n' "$(openssl passwd -apr1 '你的密码')" > deploy/.htpasswd
chmod 600 deploy/.htpasswd
```

用 `openssl passwd -apr1` 而不是存明文，是因为 nginx 支持 apr1 哈希格式，文件泄露也不直接暴露密码。`apr1` 这东西在不同系统上名字不一样，Apache 的 `htpasswd` 命令也行，但 CVM 上不一定有，`openssl` 一定有。

## 十一、第九步：构建与启动

```bash
docker compose -f deploy/docker-compose.yml up -d --build
```

这一步最容易出问题的认知是：**构建时的网络和运行时的网络不是一回事。**

服务跑起来之后能访问 DeepSeek、能访问硅基流动，说明运行时的出网是通的。但构建时 pip 拉包、npm 拉依赖走的是另一条路，可能是另一个源、另一套限速。

今天就在这上面栽了一次，见第九节第 2 条。

一个实用的做法：把构建期的源也写进配置，别依赖默认值。

```bash
# deploy/.env（compose 会自动从 compose 文件所在目录读取）
PIP_INDEX_URL=https://mirrors.cloud.tencent.com/pypi/simple
NPM_REGISTRY=https://registry.npmmirror.com
```

## 十二、第十步：分层验收

「页面能打开」不算通过。这次是分五层验的，每一层单独确认：

| 层 | 怎么验 | 期望 |
|---|---|---|
| 容器 | `docker compose ps` | 四个都 healthy |
| 进程 | 本机 `curl 127.0.0.1/health` | 200 |
| 鉴权 | 不带凭证访问首页 | 401 |
| 鉴权 | 带凭证访问首页和 API | 200 |
| 业务 | 发一句话看流式回复 | SSE 事件完整 |

为什么要分层：**每一层坏掉的表现不一样，而且指向完全不同的方向**。

容器不健康是启动问题。健康检查 200 但首页 502 是反代问题。401 是鉴权规则生效了但凭证不对。500 是鉴权文件本身打不开，完全是另一回事。业务层要单独验，因为前面全绿也可能 LLM 的 key 是错的。

分层验完，你才知道「哪里坏了」而不是只知道「坏了」。

## 十三、这次踩的四个坑

按发生顺序记，每条都写清楚现象、定位在哪一层、根因、怎么修的。这一节是整篇文档最有价值的部分，因为下次你大概率还会撞上类似的东西。

### 坑一：加了鉴权，容器变 unhealthy

现象：`docker ps` 里 web 从 healthy 变成 unhealthy，但公网访问一切正常。

定位层：容器健康检查，不是应用层。

根因：`Dockerfile.web` 的 HEALTHCHECK 打的是 `http://127.0.0.1/`，加了 `auth_basic` 之后这个请求返回 401。nginx 镜像里的 wget 是 busybox 版本，遇到 401 返回退出码 1，探针永远失败。

这个坑的杀伤力比看起来大：compose 里 web 依赖 `backend` 的健康状态，探针一直失败，整条启动链会卡住。

修法：探针改打 `/health`，并在 nginx 里给这个路径单独 `auth_basic off`。健康检查接口本来就不该要求鉴权，负载均衡、监控、探针走的都是它。

### 坑二：PyPI 直连，构建卡死在一个包上

现象：`docker compose build` 在 pip 阶段失败，前两个包元数据拉取正常，到 pydantic 突然崩。

报错：`Could not find a version that satisfies the requirement pydantic==2.13.3 (from versions: none)`

定位层：构建阶段的包索引拉取，不是依赖声明写错了。

根因：这个版本在本地干净环境里装过，确实存在。`from versions: none` 这个措辞有误导性，它看起来像「这个版本不存在」，实际是索引页根本没拉下来，pip 静默降级成了「没有可用版本」。

实测对比很有说服力：同一台机器上访问 pypi.org 的 pydantic 索引页，10 秒超时；访问腾讯云镜像，0.24 秒返回 200。差四十倍。

修法：覆盖 `PIP_INDEX_URL`。

教训：遇到「找不到版本」先别改版本号，先单独 curl 一下索引页量延迟。改版本号是最容易走错的方向。

### 坑三：密码文件权限 600，带正确密码反而 500

现象：四个容器全 healthy，`/health` 正常，无凭证访问正确返回 401，但带正确密码访问返回 500。

报错：`[crit] open() "/etc/nginx/.htpasswd" failed (13: Permission denied)`

定位层：容器内进程权限。

根因：宿主机上按文档 `chmod 600`，Docker 的 `COPY` 会把权限原样带进镜像，容器里就是 `-rw------- root root`。nginx 主进程是 root 能读，但**处理请求的 worker 进程是 nginx 用户**，读不到，鉴权阶段直接 500。

修法：Dockerfile 里 COPY 之后显式放宽：

```dockerfile
COPY deploy/.htpasswd /etc/nginx/.htpasswd
RUN chmod 644 /etc/nginx/.htpasswd
```

宿主机上保持 600（只有部署用户可读），镜像内放宽到 worker 可读。两边的权限要求本来就不一样，跨 COPY 边界时必须显式声明。

教训：401 和 500 的区别很有诊断价值。401 说明门在、钥匙不对；500 说明门本身坏了。看到 500 先怀疑文件、权限、路径，不要怀疑密码。

### 坑四：git pull 抖了一下

现象：部署脚本里 `git pull && docker compose up` 整条链没走完，日志里只有一个 `EXIT=1`。

定位层：代码传输。

根因：从国内访问 github.com 延迟 6.9 秒，首次拉取超时。重试一次就成功了。

修法：重试。但要有意识地重试，而不是无脑循环。先量一次延迟，确认是网络抖动而不是凭证问题、分支问题。

教训：`&&` 链式命令里任何一环失败，后面的都不执行，而输出可能只剩一个退出码。排查时第一步是把命令拆开单独跑，看是哪一环断的。

## 十四、提炼出来的判断规则

这些是能迁移到下一个项目的东西。具体命令会忘，这些不会。

一、**部署不是从装 Docker 开始的，是从清点依赖开始的。** 你能列出所有依赖，才谈得上复现。

二、**本地跑不通就别上服务器。** 一次只引入一个新变量。

三、**容器里的 localhost 永远是容器自己。** 见到 localhost 就想到要换服务名。

四、**端口有两道门。** 容器的端口映射，和云厂商的安全组。两道都开才通。

五、**连接被拒和连接超时是两个方向。** 前者是没服务在听，后者是被挡住。先分清再动手。

六、**401 和 500 也是两个方向。** 401 是凭证问题，500 是配置或权限问题。

七、**构建时的网络不等于运行时的网络。** 出网能通不代表构建能通。

八、**探针、监控、负载均衡走的路径要豁免鉴权。** 否则健康检查会假死，而假死比真死更难查。

九、**跨 COPY 边界的文件权限要显式声明。** 宿主机的要求和容器里的要求不是一回事。

十、**软依赖要实测降级，不能靠推断。** 「我以为它能降级」不算数。

## 十五、附录：命令速查

```bash
# 本地起栈（带构建）
docker compose -f deploy/docker-compose.yml up -d --build

# 看状态
docker compose -f deploy/docker-compose.yml ps

# 看日志
docker compose -f deploy/docker-compose.yml logs -f backend

# 进容器排查
docker compose -f deploy/docker-compose.yml exec backend sh

# 停掉但保留数据
docker compose -f deploy/docker-compose.yml down

# 重新起（不构建）
docker compose -f deploy/docker-compose.yml up -d --no-build

# 只重建某个服务
docker compose -f deploy/docker-compose.yml up -d --build web

# 服务器上目录权限（后端非 root，uid 10001）
sudo chown -R 10001:10001 data logs

# 生成鉴权密码文件
printf 'admin:%s\n' "$(openssl passwd -apr1 '你的密码')" > deploy/.htpasswd

# 校验 nginx 配置
docker exec <web容器名> nginx -t
```

排查顺序的口诀：先 `ps` 看谁没起来，再 `logs` 看报错，再 `exec` 进容器验证网络和文件，最后才改代码。

顺序别颠倒。大多数人一上来就改代码，那是最后一步。
