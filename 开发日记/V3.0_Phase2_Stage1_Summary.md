# V3.0 第四期纯干货日记：语义路由加固

## 核心目标

第二阶段（改旧）的第一个任务——任务 2.1（语义路由加固）。三个目标：**引入置信度评分、加入前置正则快速通道、低置信度走向澄清反问而非强行猜测。**

共涉及 5 个文件——3 个新增/修改（schemas.py、router_service.py、clarification_service.py），2 个上游接入（chat.py、config.py），附带修复 2 个测试文件（test_health.py、test_auth_service.py）。

---

## 核心变革一：置信度评分体系

### 之前的问题

`RouterResult` 只有 `intent` 和 `keywords` 两个字段。`analyze_intent` 是一个"一次定生死"的硬路由——无论模型有多大把握，返回结果没有任何"确定程度"的标注。上游 chat.py 只能无条件信任路由结果，遇到边界模糊的输入要么强行猜测，要么走到 `else` 分支返回"我不太明白"。

### 修复方式

**schemas.py**：`RouterResult` 新增 `confidence: float = Field(default=1.0, ge=0.0, le=1.0)`。默认值为 1.0 确保向后兼容——旧的调用代码不传 confidence 也不会报错。`ge=0.0, le=1.0` 是 Pydantic 的取值约束，非法数据在对象创建瞬间就被拦住。

**router_service.py**：LLM 的 system prompt 增加了 confidence 评分指引——"1.0 完全确定、0.8-0.9 比较确定、0.4-0.5 不太确定、0.0-0.3 几乎无法判断"，并在示例中加入了低置信度场景（"那个东西怎么弄啊" → confidence=0.4）。

## 核心变革二：前置正则快速通道

### 之前的问题

所有请求不管多明确都走 LLM。即使是"汇率"→tool、"你好"→chitchat 这种一眼能定的意图，也得去智谱走一圈，每次 1-3 秒外加 token 成本。

### 修复方式

**router_service.py**：新增 `INTENT_RULES` 规则表，6 条高频规则（汇率、天气、查订单、制度咨询、投诉、打招呼），在 `analyze_intent` 函数顶部先过正则循环，命中直接 `return RouterResult(confidence=1.0)`，跳过 LLM。

设计要点：
- 规则用 `re.search` 匹配（包含即触发），只有打招呼规则用 `^...$` 锚定防止"你好查订单"误吞
- 顺序即优先级——第一条命中的直接返回，后面的规则不再检查
- 规则命中时 confidence 固定为 1.0，与 LLM 的高置信度输出语义一致

## 核心变革三：低置信度澄清流程

### 之前的问题

置信度低于阈值时，原有代码没有处理路径——要么强行猜测执行错误的分支，要么在 `else` 返回硬编码的"我不太明白"。没有"我认为可能是 XX，但不太确定，反问确认一下"的能力。

### 修复方式

**clarification_service.py（新建）**：轻量澄清服务，暴露 `generate_clarification(user_input, router_result) → str`。只有一轮 LLM 调用，不带历史上下文，prompt 要求基于初步路由结果生成自然反问。

关键设计取舍——不把澄清逻辑塞进 chitchat 分支，原因是：
1. **语义污染**：澄清被记录为 chitchat，日志数据不干净
2. **Prompt 冲突**：chitchat 的"热情幽默"语气与澄清的"审慎确认"语气矛盾
3. **记忆污染**：澄清内容混入历史上下文，干扰后续对话
4. **Token 浪费**：chitchat 加载全量历史，澄清只需要用户原文 + 路由结果

**chat.py**：在 `analyze_intent` 之后、`stream_generator` 之前插入置信度检查。`confidence < CLARIFICATION_CONFIDENCE_THRESHOLD` 时，定义独立的 `clarification_stream()` 处理 SSE 推送并返回，不走后面的 if-elif 四个分支。原有流式生成逻辑一行不动。

**config.py**：`CLARIFICATION_CONFIDENCE_THRESHOLD` 写入配置层，默认 0.6，环境变量可覆盖。

## 附带修复

### test_health.py：SSE 响应解析

`test_chat_endpoint_stores_and_replies` 测试一直埋着一个 bug——聊天端点返回的是 `StreamingResponse`（SSE 多行数据），但测试用 `response.json()` 解析，导致 `JSONDecodeError`。之前 32 个测试都忽略了这一个失败？不，更可能的情况是它从来没跑通过，只是没被发现。

修复方式：新增 `_parse_sse_events` 和 `_extract_full_reply` 两个辅助函数，把 SSE 响应体解析为事件列表，再从中提取完整回复内容进行断言。

### test_auth_service.py：AsyncMock 的误用

`mock_session = AsyncMock()` 一刀切导致 `db.add(user)` 返回了一个无人 await 的协程，Python 报了 `RuntimeWarning: coroutine was never awaited`。SQLAlchemy 的 `add` 是同步方法，`commit`/`execute` 才是异步方法。修复方式：`mock_session = MagicMock()`，只把 `execute`、`commit`、`refresh` 单独设为 `AsyncMock`。

## 面试复盘与架构反思

### 1. 正则规则的顺序陷阱

`INTENT_RULES` 是线性遍历的，第一条命中的直接 return。这意味着规则顺序直接影响路由行为。典型的冲突场景：

> "全国都在下雨我的快递能准确送到吗？"

语义上是查快递，但正则先匹配到"下雨"→tool/天气，快递查询被吞掉。反过来放"快递"在"下雨"前面→天气查询被快递吞掉。

**根因**：正则本身就是二值逻辑，不支持"同时匹配多个意图"。这不是规则写得不够细致的问题，是整个架构没有设计多意图并行能力。

### 2. 单意图路由的边界

目前的路由器（无论正则还是 LLM）设计上就是单次返回一个 intent。遇到"今天下雨吗？顺便查快递"这种多任务请求，即使用大模型分析也只能"强行选择一个"。要真正支持多任务，需要把 `RouterResult.intent` 从单个字符串改成列表，或者引入任务队列式的编排层。

单意图方案足够覆盖 80% 的客服场景（用户一次只问一个问题），但明确知道自己在这个 20% 上有缺口，比假装没看到更重要。

### 3. Decorator 只看到输入和输出

作业环节中尝试用装饰器在函数外部加日志，发现一个关键限制：**装饰器只能看到函数的输入和输出，看不到函数内部的执行路径**。`analyze_intent` 可能在正则循环里 return，也可能在 LLM 调用后 return，装饰器拿到的是同一个 `RouterResult`，无法区分来源。

这个限制不是 Python 的问题，是设计模式的选择——如果你需要在函数内部的不同分支做不同的事情，要么直接在分支上加代码，要么把不同分支拆成多个函数。

### 4. Pydantic Field 的职责

`Field(default=1.0, ge=0.0, le=1.0)` 做了三件事，但三件事的受益者不同：
- `default=1.0` → 调用方：不传也能用，向后兼容
- `ge=0.0, le=1.0` → 系统稳定性：非法数据在创建瞬间被拦截
- `description=...` → 文档消费者：Swagger 页面自动展示字段说明

在写 `Field` 之前问自己：这个字段被谁使用？需要什么约束？边界值是什么？回答这三个问题比死记硬背 API 更重要。
